With up to about 10,000 examples, the usual split is **60 / 20 / 20**. With more than a million, 1% is already plenty to evaluate on, so the split becomes about **98 / 1 / 1**.

The **dev set** (or cross-validation set) is where models are compared; the **test set** gives an unbiased estimate at the end. Both must come from the same distribution: the data the model will meet in production. The training set can come from another distribution, often a larger one that is easier to collect.

The **train-dev set** has the same distribution as the training set, but is not used for training. It tells a variance problem apart from a data mismatch.

<Section n="03" title="What to try next" id="improve">

<div class="note-fixes">

<div class="note-fix note-fix--bias">
<span class="note-fix-label">Avoidable bias</span>

- train a bigger model
- train longer
- a better optimisation algorithm: momentum, RMSprop, Adam
- another architecture: activation functions, CNN, RNN

</div>

<div class="note-fix note-fix--variance">
<span class="note-fix-label">Variance</span>

- get more data
- data augmentation
- regularisation: L2, dropout
- another architecture: activation functions, CNN, RNN

</div>

<div class="note-fix note-fix--mismatch">
<span class="note-fix-label">Data mismatch</span>

- carry out a manual error analysis
- make the training data more like the dev set
- clean up incorrectly labelled data

</div>

<div class="note-fix note-fix--devfit">
<span class="note-fix-label">Overfitting the dev set</span>

- get a bigger dev set

</div>

</div>

</Section>

<Section n="04" title="Metrics" id="metrics">

For a binary classifier, every prediction falls into one of four boxes: right or wrong, for a positive or a negative.

<ConfusionMatrix />

Accuracy alone can mislead when one class is rare: a model that always predicts "negative" scores 99% if only 1% of the samples are positive. Precision, recall and their F1 score tell the real story.
